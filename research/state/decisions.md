# Decisions

Architecture and evidence decisions are recorded here. Each decision states the
context, choice and consequence; it is not a research result.

## D-001 - Repository-native harness

**Context:** The project needs to work with DeepSeek, Claude, GPT, Gemini,
OpenCode and terminal agents across long sessions.

**Decision:** Use Markdown role/procedure files, JSON records and Python
standard-library tools. Do not adopt a multi-agent framework as a dependency.

**Consequences:** No hidden scheduler or database; the lead must assign work.
The same files remain readable by humans and any model. A host with subagents can
parallelize using the handoff contract.

## D-002 - Single lead plus on-demand specialists

**Context:** Most tasks need one coherent decision-maker, but compiler,
statistics, mathematics and review expertise conflict if loaded at once.

**Decision:** Keep one Research Lead and six specialist role files. Load one role
at a time. A Critical Reviewer receives only the claim and evidence, not the full
author transcript.

**Consequences:** Low context use and explicit responsibility. The lead can
still be wrong; review gates and independent/human review remain necessary.

## D-003 - Markdown for state, JSON for records

**Context:** Humans need readable progress; tools need unambiguous IDs, statuses
and paths.

**Decision:** Keep a short `research/state/index.md` and a machine-readable
`hypotheses.json`; keep experiment/claim records as JSON with linked Markdown
notes.

**Consequences:** Some duplication is unavoidable, but summaries stay short and
the validator can check records without parsing prose.

## D-004 - Custom semantic validator, documented JSON Schemas

**Context:** Python `jsonschema` is not guaranteed to be installed; the
repository must work offline.

**Decision:** Provide JSON Schema files for external tools, but implement the
required checks with the Python standard library. The validator also checks
cross-record IDs, artifact existence, status/review rules and toolchain
consistency.

**Consequences:** No extra dependency. The validator is intentionally narrower
than full JSON Schema; schema files remain the field documentation.

## D-005 - No automatic promotion of claims

**Context:** A convincing narrative generated by an LLM is not evidence.

**Decision:** `supported` requires validated evidence plus independent or human
review. Mathematical `proved` requires an audited proof. Self-review is labelled
`model-assisted-self-review`.

**Consequences:** Some results stay `analyzed` or `inconclusive` longer. That is
intended.

## D-006 - Upstream actions require human approval

**Context:** LLVM's AI policy requires a human in the loop, disclosure and
non-extractive contributions.

**Decision:** Local experiments are allowed. No agent may post PRs/issues/comments
or prepare an upstream submission without explicit human review and disclosure.

**Consequences:** Slower upstream path, lower risk of extractive or incorrect
contributions.

## D-007 - Stage 0 remains mixed and unvalidated

**Context:** Stage 0 used clang 23.1.5 with LLVM 24.0.0git and `ir_compat.py`.

**Decision:** Preserve Stage 0 as recorded, label it baseline-specific and make
R1-A the first R1 workstream. Do not rewrite old results.

**Consequences:** R1 cannot skip the consistent-toolchain validation. Stage 0
mechanisms are hypotheses, not final evidence.

## D-008 - Documentation-only simulation record

**Context:** The harness must demonstrate handoff/review/checkpoint without
executing an LLVM campaign or fabricating measurements.

**Decision:** Include `SIM-0001-handoff-smoke` as a simulation record with no
timings and no performance claim. It exercises roles, handoff, review and
validation only.

**Consequences:** The record demonstrates the workflow but cannot support a
scientific claim. It is excluded from performance evidence.

## D-009 - Toolchain provenance is a manifest, not a version string

**Context:** clang 23.1.5 and locally built LLVM 24.0.0git can both report
plausible version numbers while differing in source revision and build
configuration. PATH discovery can silently select the wrong binary.

**Decision:** Strict experiment readiness requires an explicit toolchain
manifest with full LLVM source SHA, source/build directories, CMake settings,
absolute binary paths, SHA-256 hashes and recorded version output. States are
`verified`, `matched`, `mixed` and `unverified`; only `verified` is acceptable
for `analyzed` or later experiment records.

**Consequences:** A build with matching version strings still needs a manifest.
`doctor.py --experiment` fails without one. Structural provenance is necessary
but does not independently prove how an external release binary was produced.

## D-010 - Schema subset plus semantic gates

**Context:** Parsing a schema file does not validate records. The repository
cannot assume `jsonschema` is installed.

**Decision:** Implement an explicit, documented Draft 2020-12 subset in
`scripts/research/schema_lite.py`, reject unsupported schema keywords, and keep
repository-specific semantic checks for provenance, status transitions,
artifact existence and review gates.

**Consequences:** The contract is consistent and offline. It is not full JSON
Schema; unsupported constructs fail loudly instead of being ignored. Structural
validation cannot certify mathematical truth or scientific validity.

## D-011 - Evidence gates require review artifacts

**Context:** Labels such as `proved`, `validated` and `supported` were previously
too easy to assert with only a status string.

**Decision:** `proved` requires a proof artifact, a review artifact, reviewer
identity/type, an accept decision and zero unresolved obligations.
`numerically-checked` requires actual check artifacts. `supported` requires
validated evidence, raw timings, validation artifacts, a review artifact and
independent/human review. Self-review by the same model remains
`model-assisted-self-review`.

**Consequences:** More records remain `analyzed` or `under-review`; this is
intended. A human or genuinely separate agent is still required for promotion.

## D-012 - R1 evidence stays self-reviewed and provisional

**Context:** R1-A reproduced the main Stage 0 effects on a matched toolchain, but
all measurements came from one machine, without hardware counters, and were
reviewed by the same model that produced them. The local R1-F patch modifies the
compiler and is not covered by the verified base toolchain manifest.

**Decision:** Keep R1-A, R1-C, R1-D and the mathematical claims at `analyzed`,
`inconclusive` or `numerically-checked`/`working-proof`. Do not mark them
`supported` or `proved`. Record the R1-F prototype as `inconclusive` because the
patched `opt` is outside the verified provenance manifest, even though its
measurements are preserved.

**Consequences:** Reports must state the self-review and provenance limits. A
future human or independent-reviewer pass is required before any upstream
proposal or novelty claim. This is deliberate, not an infrastructure failure.

## D-013 - Randomized complete blocks and paired ratios

**Context:** R1 used an unrecorded shuffled order, treated internal trials as
independent, and compared separately bootstrapped intervals to a fixed A median.
Some small effects were overinterpreted.

**Decision:** Every new measurement is a randomized complete block: A/B/C/AA each
appear once per block, the seed and schedule are stored, within-process trials
are aggregated to a process median, and inference uses paired block ratios with
a block bootstrap. A/A is a noise gate. Evidence labels are explicit and small
effects remain provisional.

**Consequences:** Small effects need more blocks or remain inconclusive. The old
descriptive intervals remain historical artifacts, not corrected evidence.

## D-014 - Predictor features are separated by availability

**Context:** The R1 predictor used post-fusion YMM counts as a decision feature
and summed absolute percentages as "runtime-weighted regret".

**Decision:** Only static pre-treatment features, scenario context and the
current compiler's own decision may enter a policy. Post-fusion assembly,
measured runtimes and counters are diagnostic-only. Regret is absolute runtime
above the per-point A/B oracle with explicit equal-case weighting. R1.1 results
are an in-sample screen, not a deployable model.

**Consequences:** Some predictors are unevaluable until static extraction is
stronger, and the R1 two-signal numbers cannot be reused as validation.
